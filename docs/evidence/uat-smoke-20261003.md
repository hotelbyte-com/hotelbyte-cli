## Smoke finding fixed during this run

Items ran first at branch tip `565fc9e`. Item 2 exposed a real bug:
`/api/view/getApiPaths` returns `data = { methodMetas: [...], total }`, while
`fetchCatalog` only accepted a bare array — every catalog pull failed with
`[500] unexpected /api/view/getApiPaths response`. Fixed in `1545982`
(`src/core/api_catalog.ts` now accepts both shapes; stub test added for the
live envelope). All results below were (re-)executed at `1545982` unless noted.

### 4. Write guard, both directions — `trade/tenant/labelOrder` (nonexistent order id)

Without `--confirm` — rejected locally, never sent:

```
$ hbcli api call trade/tenant/labelOrder --data '{"orderId":"HBCLI-SMOKE-NX-000","label":"hbcli-smoke"}'
✗ /api/trade/tenant/labelOrder looks like a WRITE operation
  (method name "LabelOrder" is not on the read-prefix list). Re-run with --confirm to execute.
# exit=1, stdout empty — guard fires at src/commands/api.ts:150-166 before any HTTP call
```

With `--confirm` — request goes out, server answers:

```
$ hbcli api call trade/tenant/labelOrder --data '{"orderId":"HBCLI-SMOKE-NX-000","label":"hbcli-smoke"}' --confirm
✗ [400] /api/trade/tenant/labelOrder: {"code":100000400,"msg":"invalid request: invalid ID string: HBCLI-SMOKE-NX-000"}
# exit=1 — SERVER-side validation envelope: outbound + through the auth chain proven
$ hbcli api call trade/tenant/labelOrder --data '{"orderId":"999999999999","label":"hbcli-smoke"}' --confirm
{}                                        # exit=0 — server accepted (no-op for nonexistent id)
```

The numeric-id probe returned a success envelope with empty data — the UAT
handler does not 404 on unknown ids. No real order exists at that id and no real
order was modified; the demo tenant is a shared sandbox identity.
